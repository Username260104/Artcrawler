# 기본 구현 계획

## 1. 목표

첫 버전의 목표는 단순하다.

사용자가 웹을 열면 달력을 보고, 권위 있는 한국 동시대 미술 전시가 언제 열리고 언제 끝나는지 확인할 수 있어야 한다.

이 단계에서는 전시 추천, 지도 기반 탐색, 계정, 북마크, 리뷰, 티켓 예매, 편집 콘텐츠를 만들지 않는다. 핵심은 전시 기간을 공식 출처 기반으로 수집해서 달력에 정확하게 보여주는 것이다.

## 2. 제품 범위

### 포함한다

- 월간 달력 화면
- 날짜 선택 시 해당 날짜에 진행 중인 전시 목록
- 전시별 기본 정보
- 공식 출처 링크
- 기관/갤러리 필터
- 백그라운드 자동 크롤링
- 크롤링 실행 로그
- 크롤링 실패 시 사용자 화면 보호

### 포함하지 않는다

- 전시 정보 수동 입력 운영
- 사용자 계정
- 북마크
- 개인화 추천
- 티켓/예약 연동
- 비평/리뷰 콘텐츠
- 지도 우선 탐색
- 인스타그램 중심 수집
- 전국 전체 전시 커버리지
- 모든 갤러리 동시 지원

중요한 전제:

전시 정보는 사람이 매번 입력하는 방식이 아니라, 공식 사이트에서 자동 수집한다. 다만 수집 대상 기관 목록은 코드 또는 데이터베이스의 `Venue Registry`로 관리한다. 이것은 전시 수동 입력이 아니라 수집 대상 설정이다.

## 3. 첫 화면

첫 화면은 랜딩 페이지가 아니라 달력이다.

기본 화면:

- 현재 월 달력
- 오늘 날짜 강조
- 전시 기간 표시
- 진행 중 전시와 예정 전시 구분
- 종료 임박 전시 표시

날짜를 선택하면:

- 해당 날짜에 볼 수 있는 전시 목록을 보여준다.
- 각 전시는 제목, 작가, 장소, 기간, 공식 링크를 가진다.

첫 버전이 답해야 하는 질문:

1. 지금 볼 수 있는 전시는 무엇인가?
2. 곧 시작하는 전시는 무엇인가?
3. 곧 끝나는 전시는 무엇인가?

## 4. MVP 전시 데이터

최소 전시 정보:

```text
전시 제목
작가명
장소
시작일
종료일
상태
공식 출처 URL
이미지 URL
수집 신뢰도
마지막 확인 시각
```

상태 계산:

```text
예정: 시작일 > 오늘
진행 중: 시작일 <= 오늘 <= 종료일
종료 임박: 진행 중이고 종료일이 7일 이내
종료: 종료일 < 오늘
```

설명문은 MVP 필수 데이터가 아니다. 긴 보도자료나 전시 서문을 긁어오는 것은 저작권, 품질, 유지보수 문제가 생길 수 있으므로 후순위로 둔다.

## 5. MVP 기관 범위

기준은 대중적 인지도보다 동시대 미술 씬 안에서의 권위다.

선정 기준:

- 동시대 미술 프로그램의 지속성
- 한국 및 국제 미술 담론에서의 영향력
- 주요 작가 또는 주요 기획 전시 이력
- 서울 미술 동선 안에서의 실질적 존재감
- 공식 전시 페이지 또는 아카이브 존재
- 주기적으로 공개 전시를 여는지 여부
- 크롤링 가능한 공식 웹사이트 구조

초기 후보:

### 미술관/기관

- 국립현대미술관 서울
- 서울시립미술관
- 리움미술관
- 아트선재센터
- 송은
- 아모레퍼시픽미술관

### 국내 주요 갤러리

- 국제갤러리
- 갤러리현대
- PKM 갤러리
- 아라리오갤러리
- 갤러리바톤
- 바라캇 컨템포러리

### 서울 프로그램이 있는 글로벌 갤러리

- Pace Seoul
- Perrotin Seoul
- Lehmann Maupin Seoul
- White Cube Seoul
- Thaddaeus Ropac Seoul
- Gladstone Seoul
- Esther Schipper Seoul

이 목록은 약 18곳이다. 하지만 첫 배포가 18곳 전체를 모두 지원해야 하는 것은 아니다. 현실적인 첫 배포 기준은 6-10곳의 안정적인 자동 수집이다. 나머지는 수집 대상 목록에 등록하되, adapter가 안정화되기 전까지 비활성 상태로 둘 수 있다.

## 6. 수집 방식

사용자가 사이트에 접속할 때마다 크롤링하지 않는다.

사용자 화면은 데이터베이스만 읽는다. 크롤링은 예약 작업으로 백그라운드에서 실행한다.

흐름:

```text
공식 웹사이트
-> 예약 크롤러
-> 원문 HTML/JSON 저장
-> 기관별 파서
-> 전시 데이터 정규화
-> 데이터베이스 upsert
-> 달력 화면
```

이 방식의 이유:

- 페이지가 빠르게 열린다.
- 특정 갤러리 사이트가 느리거나 죽어도 사용자 화면은 깨지지 않는다.
- 크롤링 실패를 별도로 재시도할 수 있다.
- 출처 구조 변경을 추적할 수 있다.
- 각 기관이 마지막으로 언제 확인됐는지 알 수 있다.

수집 주기:

- MVP: 하루 1회
- Frieze Seoul, Kiaf 등 전시 변동이 많은 기간: 하루 2회 이상 검토

## 7. 크롤러 구조

만능 크롤러 하나를 만들지 않는다.

갤러리와 미술관 사이트는 구조가 제각각이다. 따라서 기관별 adapter를 만들고, 모든 adapter가 같은 형식의 전시 데이터를 반환하게 한다.

예상 구조:

```text
src/
  crawlers/
    registry.ts
    run-crawler.ts
    adapters/
      pace.ts
      white-cube.ts
      perrotin.ts
      ropac.ts
      kukje.ts
      gallery-hyundai.ts
    shared/
      date-range.ts
      normalize-text.ts
      upsert-exhibition.ts
```

adapter 반환 형식:

```ts
type ParsedExhibition = {
  venueSlug: string
  title: string
  artists: string[]
  startDate: string
  endDate: string
  sourceUrl: string
  imageUrl?: string
  confidence: number
  raw?: unknown
}
```

기본 원칙:

- 정적 HTML은 `fetch`와 `cheerio`로 처리한다.
- JavaScript 렌더링이 필요한 사이트만 `Playwright`를 쓴다.
- 모든 파싱 결과는 `zod`로 검증한다.
- 낮은 신뢰도의 결과는 공개 데이터로 바로 반영하지 않는다.

## 8. 데이터베이스 모델

최소 모델:

```text
Venue
- id
- name
- slug
- type: museum | gallery | nonprofit
- authorityTier
- district
- officialUrl
- exhibitionUrl
- crawlerKey
- crawlerEnabled
- createdAt
- updatedAt

Exhibition
- id
- venueId
- title
- artists
- startDate
- endDate
- status
- sourceUrl
- imageUrl
- confidence
- sourceHash
- firstSeenAt
- lastSeenAt
- createdAt
- updatedAt

CrawlRun
- id
- venueId
- status: success | partial | failed
- fetchedCount
- parsedCount
- errorMessage
- startedAt
- finishedAt
```

중요 필드:

- `sourceHash`: 같은 전시가 여러 목록에서 중복 수집되는 것을 줄인다.
- `confidence`: 파싱 결과의 신뢰도를 표현한다.
- `lastSeenAt`: 공식 사이트에서 마지막으로 확인된 시점을 기록한다.
- `crawlerEnabled`: 권위 있는 기관 목록과 실제 활성화된 크롤러를 분리한다.

## 9. 달력 UI 요구사항

처음에는 예쁜 타임라인보다 읽기 쉬운 달력이 중요하다.

필수 조작:

- 이전/다음 달 이동
- 오늘로 이동
- 날짜 선택
- 선택한 날짜의 전시 목록 보기
- 기관 유형 필터
- 공식 출처 열기

표시 규칙:

- 전시는 시작일부터 종료일까지 활성 상태로 계산한다.
- 달력 칸 안에 너무 많은 정보를 넣지 않는다.
- 날짜 칸에는 주요 전시 몇 개만 보이고, 자세한 목록은 옆 영역이나 아래 목록에서 보여준다.
- 모바일에서는 달력보다 날짜별 리스트 가독성을 우선한다.

## 10. 기술 스택

권장 기본 스택:

- Next.js
- Postgres
- Prisma
- Cheerio
- Playwright
- Zod
- Vercel Cron 또는 GitHub Actions

초기에는 가장 단순하게 배포 가능한 방식을 택한다. 크롤러가 무거워지면 나중에 별도 worker로 분리한다.

## 11. 구현 단계

### 1단계: 기반

- 앱 스캐폴딩
- 데이터베이스 스키마 작성
- Venue Registry 작성
- 초기 기관 목록 등록
- 개발용 fixture 전시 데이터 추가
- 달력 API 작성

완료 기준:

- 개발용 fixture 데이터로 달력이 렌더링된다.

### 2단계: 달력 MVP

- 월간 달력 구현
- 날짜 선택 구현
- 날짜별 전시 목록 구현
- 상태 표시 구현
- 기관 유형 필터 구현
- 공식 링크 연결

완료 기준:

- 사용자가 오늘, 이번 주, 이번 달 볼 수 있는 전시를 확인할 수 있다.

### 3단계: 첫 자동 수집

- 안정적인 공식 사이트 3곳 adapter 구현
- 추천 시작점: Pace, White Cube, Perrotin
- 파싱 결과 검증
- DB upsert 구현
- CrawlRun 로그 저장

완료 기준:

- 실제 공식 출처에서 수집된 전시가 달력에 표시된다.

### 4단계: 권위 기관 확장

- adapter를 한 곳씩 추가한다.
- 권위와 크롤링 안정성을 함께 본다.
- 불안정한 기관은 등록만 하고 비활성화한다.
- 실패 로그를 확인 가능하게 만든다.

완료 기준:

- 6-10곳의 권위 있는 기관/갤러리가 안정적으로 자동 갱신된다.

### 5단계: 운영 안정화

- 하루 1회 예약 크롤링 설정
- 중복 감지 보강
- 날짜 파싱 테스트 작성
- adapter별 저장 HTML fixture 테스트 작성
- 반복 실패 감지

완료 기준:

- 사용자가 접속하지 않아도 전시 데이터가 주기적으로 갱신된다.
- 크롤링 실패가 사용자 화면을 망가뜨리지 않는다.

## 12. 주요 리스크

### 공식 사이트 구조 변경

갤러리 사이트는 언제든 바뀐다. adapter를 작게 유지하고, fixture 테스트를 둔다.

### 날짜 파싱

영문 날짜, 국문 날짜, 월만 표기된 날짜, 연도 생략 날짜가 섞일 수 있다. 날짜 파싱은 공통 모듈로 분리한다.

### 중복 전시

현재 전시, 예정 전시, 장소 페이지, 상세 페이지에 같은 전시가 반복될 수 있다. `venueId + 정규화된 제목 + 날짜 범위`와 `sourceHash`로 중복을 줄인다.

### 권위는 있지만 수집이 어려운 공간

일부 공간은 PDF, 이미지, 인스타그램 중심으로 공지할 수 있다. 이런 공간은 MVP를 막지 않는다. 등록은 하되, 수집 안정화는 후순위로 둔다.

### 달력 과밀

전시는 보통 몇 주 이상 지속되기 때문에 달력 칸이 금방 복잡해진다. 달력은 방향감만 주고, 세부 정보는 리스트에서 보여주는 구조가 필요하다.

## 13. MVP 완료 기준

MVP는 다음 조건을 만족하면 완료로 본다.

- 웹 첫 화면이 달력이다.
- 달력은 공식 출처에서 자동 수집된 전시를 보여준다.
- 사용자는 날짜를 선택해 그날 볼 수 있는 전시를 확인할 수 있다.
- 사용자는 미술관/갤러리 필터를 사용할 수 있다.
- 각 전시는 공식 출처 링크를 가진다.
- 크롤링은 접속 시점이 아니라 예약 작업으로 실행된다.
- 크롤링 실패는 로그로 남고 사용자 화면은 유지된다.
- 최소 6곳의 권위 있는 기관/갤러리가 안정적으로 자동 갱신된다.
